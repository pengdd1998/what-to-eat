|---|---|---|---|---|

## 二、加权评分表（1–5 分；每格附一句话理由）

| 维度（权重） | A：Next.js+SQLite 同构单体 | B：FastAPI+Postgres 多容器 | C：Umami+问卷引擎+胶水 |
|---|---|---|---|
| D1 工期（25%） | **5**：单仓单镜像单库文件，唯一对 2.5–3 人周构建预算留有余量的形态 | **3**：双载体首发+4 容器被初筛记为"挤压构建预算"，顶在 H2 上限 | **2**：初筛明示 H2 边缘通过、集成 N 系统工时可能反超自建，且尚未做工作量核算 |
| D2 运维/可用性（15%） | **5**：活动部件 2 个（app+cron），无独立数据库进程可挂，RTO 靠重建镜像即达 | **3**：4 容器（api/web/db/cron）故障域最大，Postgres 升级/备份/恢复需专门流程 | **3**：多第三方容器同宿主机，任一组件崩溃或升级即进入晚餐窗故障域 |
| D3 交付节奏（10%） | **5**：单镜像分钟级发布/回滚，双版本（B-06）用环境开关即达 ≤1 分钟 | **4**：OpenAPI 契约清晰、compose 一条链发布，但多镜像联动略慢 | **2**：问卷引擎改动需读他人代码；"随便吧"注入与双版本切换在配置驱动引擎中可能做不了，被迫 fork |
| D4 性能/容量（5%） | **5**：SSR+SQLite WAL 在 ≤100 QPS/≤1GB 下余量巨大 | **5**：异步 FastAPI+Postgres 轻松达标，余量同为最大档 | **4**：组件轻量达标无虞，但多一跳页面组装对 4G 首屏 ≤2s 有轻微挤压 |
| D5 合规/数据治理（10%） | **4**：全自研数据流对 H3/H4 最可控，但 B-07/B-09 要件全靠手写、无框架护栏 | **4**：服务端缓存纪律（H4）需自觉遵守，合规要件同样手写 | **3**：Umami 自托管无出境问题，但其会话/留存/IP 处理默认值需逐条对 H3/H6 与 B-01 核对，有踩线风险 |
| D6 统计/实验（15%） | **4**：≤5,000 事件下 SQL 日表+脚本可覆盖 F-12 全口径与 Wilson CI；扣分在 JS 统计生态薄、方法升级余量小 | **5**：pandas/statsmodels 原生覆盖 Wilson CI/序贯/漏斗，F-12/F-13 支撑最强 | **2**：北极星分子分母、失效剔除、序贯分组全被 Umami 通用漏斗模型装不下，须外部双链路重算 |
| D7 可观测性（5%） | **4**：healthcheck+webhook+配额 cron 自研满足 B-03，无面板但单人不需要 | **4**：同等自研即可，Python 生态监控件多但规模用不上 | **4**：Umami 自带面板是加分，外部 API 探活仍需自研 |
| D8 团队上手（10%，固定） | **4**：Next.js 同构是当前 AI 辅助生成最主流路径，1 语言 1 框架认知面最窄 [假设：无语言偏好] | **3**：需同时握 Python 后端+JS 前端+SQL 迁移+4 容器编排，概念面最宽 [假设同上] | **2**：表面"最小自研"，实际要学 N 个系统的配置/数据模型/升级路径，单人认知负担最重 |
| D9 生态健康（5%，固定） | **5**：React/Next 生态最大、MIT、安全响应快、人才最多；SQLite 公有领域 | **5**：FastAPI（MIT）/PostgreSQL/pandas 全主流健康、许可宽松 | **3**：Umami 健康（MIT、活跃），但问卷引擎选型未定，长尾组件质量与安全记录不可预检 |
| D10 退出成本（5%，固定） | **4**：SQLite 单文件+CSV 导出迁移成本最低；TS 业务逻辑若续期换栈需重写 | **4**：Postgres 标准化最好、OpenAPI 契约资产可延续；多容器与双载体胶水沉没 | **3**：9 类事件语义绑定 Umami 数据模型，换栈需口径重映射；问卷配置资产随引擎死 |
| **加权均分（5 分制）** | **4.80** | **3.95** | **2.65** |
| **百分制总分** | **96.0** | **79.0** | **53.0** |

**前两名分差：96.0 − 79.0 = 17.0，17.0 / 96.0 = 17.7% ≥ 15% → 不触发"接近"条款（敏感性分析见第五节）。**

## 四、决策记录（ADR-001）

**状态**：已接受（Accepted）——附带第 1 周守门验证条件（见"重新评估条件"）。**2026-09-02 更新：重评条件 2 已触发**（开发者画像确认为强 Python、弱 JS），本决策转入"重新评估中"，按第五节延迟决策流程在 W1 周五前重拍——触发记录与重打分见文末附录 A。

**背景（关键数字）**：8 周时间盒（H1）；总工程量 ≤6.5–7 人周，团队 = 1 人 + AI agent（H2）；晚餐窗 17:30–21:30 可用性 ≥99.9%、RTO ≤30 分钟、RPO ≤24 小时（NFR 2.3 [假设]）；峰值 ≤50 并发 / ≤100 QPS（NFR 2.1 [假设]）；8 周埋点 ≤5,000 条 / ≤100 MB、存储上限 1GB（NFR 2.2 [假设]）；n≈30 会话/周、回访应答目标 ≥40 条；候选池 50–200 家；三大不确定点 R1（外卖可得性数据路径）、R2（深链探活×口径耦合）、R3（载体未决）；初筛 A/B/C 全部通过硬约束（B、C 带风险）。

**候选**：A（Next.js+SQLite 同构单体）、B（FastAPI+Postgres 多容器）、C（Umami+问卷引擎+胶水）。

**决策**：**选 A 为主方案**。加权总分 96.0 / 79.0 / 53.0；A−B 差 17.7% ≥ 15%，未触发延迟决策条款，允许当期拍板。

**理由（逐条对应背景）**：
1. **对 H2（6.5–7 人周、1 人 + AI）**：A 是唯一对 2.5–3 人周构建预算留有余量的形态（单仓单镜像单库）；B 的双载体+4 容器被初筛记为"挤压预算"；C 被初筛记为"集成工时可能反超自建"。
2. **对晚餐窗 99.9% / RTO ≤30 分钟**：活动部件 2 个 vs 4 个 vs N 个，单机环境下 A 故障域最小，恢复=重建镜像。
3. **对 ≤5,000 事件 / n≈30 会话/周**：统计为公式级，SQL+脚本覆盖 F-12 全口径——B 的生态优势在此规模不构成瓶颈（该判断可被 B-PoC-1 证伪，已列入重评条件）。
4. **对 R3（载体未决）**：H5-first + 纯 JSON API 与薄前端分层，是三候选中对"小程序/H5"分叉吸收能力最强的形态（spike 判小程序时加薄壳复用 API）。
5. **对 H3/H4（数据最小化 / 零 POI 落盘）**：全自研数据流端到端可控，无第三方组件数据模型的留存与口径黑盒。

**落选者否决理由**：
- **B**：非能力否决，是结构性否决——唯一显著强项（pandas/statsmodels）在 ≤5,000 事件规模无边际收益，而 4 容器运维面与双载体首发直接顶在最硬的 H2 上；若统计复杂度大增，按重评条件 4 回炉。
- **C**：在"1 人 + AI"约束下，学 N 个系统的成本高于自建小单体；且产品差异化所在（"随便吧"口径、失效剔除、序贯分组、双版本切换）恰是组件模型装不下的部分——组件覆盖的是非差异化部分。初筛已明示须先做工作量核算，本评估判定该核算大概率不利。

**后果**：
- **收益**：M1 构建第 2 周即可启动；分钟级发布/回滚支撑 M2 周迭代（NFR 2.5）；合规要件（B-07/B-09/审计）一手实现无黑盒；8 周后若续期立项，SQLite 单文件+CSV 导出迁移成本最低（D10）。
- **代价**：JS 统计生态薄——F-12 脚本需双实现交叉验证（~2 人日）；若载体判小程序，+0.5–1 人周薄壳（占用回访触达预算弹性 0.5–1 人周）。
- **新增风险与缓解**：①骨架 PoC 超时 → 触发重评条件 1；②SQLite 备份一致性 → `sqlite3 .backup` + 恢复演练 ≥2 次（B-01）；③统计口径错误 → SQL 单一事实源 + pandas 独立复算（与 R2 缓解合并，栈无关）。

**重新评估条件（信号或时间点）**：
1. **时间点：第 1 周五**（spike+骨架 PoC 收口、M1 构建启动前）——A 骨架 PoC 实际工时 >3 人日 ×1.3 → 重开 B 候选评审。
2. **信号（第 0 周必须确认）**：开发者背景若为"强 Python/数据、弱 JS"→ D8/D1 翻转、A−B 落入 <15% → 触发延迟决策流程（见第五节）。
3. **信号**：F-16 判小程序且薄壳验证 >1 人周 → 评估 API-first 形态（不必然换栈，可 A+薄壳先行）。
4. **信号**：R1 spike 落定后统计需求升级（如需序贯检验功效分析等复杂方法）→ D6 权重上调至 ≥20% 重算。
5. **时间点：8 周窗口结束**——本期决策仅对 8 周实验负责；下周期立项时按 M3 实测数据重新评估是否迁移到数据栈形态。
